# План: спейсы и мультичейн

Документ описывает переход от нынешнего Tron-only сервиса к инструменту со
спейсами и поддержкой четырёх экосистем. Он фиксирует принятые решения и их
обоснование — чтобы через полгода не пришлось выводить их заново из кода.

Статус: переименование в `walletspace` выполнено (`5628cb8`), остальное впереди.

## Целевая картина

Локальный однопользовательский инструмент, который держит несколько **спейсов**.
Спейс — это изолированный набор ключей со своей мнемоникой и своим шифрованием.
Внутри спейса живут **аккаунты**: выведенные из мнемоники или импортированные
чистым приватным ключом. У каждого аккаунта свой адрес в каждом поддержанном
**чейне** (Tron, EVM, Solana, TON), а у чейна — несколько **сетей**
(mainnet/nile, mainnet/sepolia и так далее).

Данные лежат в `~/.walletspace/`. Бинарь ставится через `go install` и через
собственный brew tap.

## Словарь

Термины ниже используются в коде, конфиге, API и UI без синонимов.

| Термин            | Что это                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| спейс (space)     | изолированный набор ключей: одна BIP39-мнемоника, опционально одна TON-мнемоника, импортированные ключи, свой пароль шифрования |
| аккаунт (account) | одна единица подписи внутри спейса: либо индекс деривации, либо импортированный ключ                                            |
| чейн (chain)      | экосистема со своей адресной моделью и своим набором операций: tron, evm, solana, ton                                           |
| сеть (network)    | конкретная сеть чейна: `tron/nile`, `evm/sepolia`, `solana/devnet`                                                              |

Важно: **адрес — свойство пары (аккаунт, чейн), а не аккаунта.** Один аккаунт
имеет четыре разных адреса. Внутри одного чейна адрес не зависит от сети.

## Принятые решения

### 1. Секреты — шифрованный keystore на спейс

Один файл `keystore.json` на спейс: argon2id для вывода ключа из пароля,
AES-256-GCM для содержимого. Внутри и мнемоника, и импортированные приватные
ключи. Расшифрованное держится только в памяти процесса.

**Почему.** Импорт чистых приватников убивает нынешний инвариант «ключи не
хранятся на диске» (см. док-комментарий `internal/wallet/store.go`): у
импортированного ключа нет мнемоники, из которой его можно вывести заново, и
секрет обязан где-то лежать. Раз лежит — должен быть зашифрован, иначе
случайный `tar` домашнего каталога или бэкап ноутбука выносит все средства.

Мнемоника переезжает в тот же keystore. Держать импортированный ключ
зашифрованным, а мнемонику, из которой выводится всё остальное, рядом в
открытом виде — защита по слабейшему звену, то есть её отсутствие.

**Что это честно даёт.** Защиту данных в покое: бэкапы, украденный диск,
чужой доступ к файлам. Это **не** защита от того, кто дотянулся до HTTP-порта,
пока спейс разблокирован — у API по-прежнему нет аутентификации.

**Ловушка, которую надо развести явно.** Появляются два пароля с совершенно
разными последствиями ошибки:

- BIP39-пасфраза (нынешний `PASSPHRASE`) — **часть деривации**. Меняешь →
  другие адреса, старые средства недостижимы.
- пароль keystore — **шифрование файла**. Меняешь → те же адреса.

Их нельзя называть одним словом в UI. Предложение: BIP39-пасфразу называть
«солью мнемоники» и прятать в раздел для опытных, пароль keystore — «пароль
спейса».

### 2. Деривация — BIP39 для трёх чейнов, отдельная фраза для TON

| Чейн   | Кривая    | Схема                  | Путь                     |
| ------ | --------- | ---------------------- | ------------------------ |
| Tron   | secp256k1 | BIP39 + BIP32          | `m/44'/195'/0'/0/{i}`    |
| EVM    | secp256k1 | BIP39 + BIP32          | `m/44'/60'/0'/0/{i}`     |
| Solana | ed25519   | BIP39 + SLIP-0010      | `m/44'/501'/{i}'/0'`     |
| TON    | ed25519   | **своя мнемоника TON** | деривации по индексу нет |

**Почему отдельная фраза для TON.** Стандартная TON-мнемоника — не BIP39: ключ
выводится через PBKDF2-HMAC-SHA512 с солью `TON default seed`. Вывести TON-ключ
из BIP39-фразы технически можно, но полученный адрес не откроется ни в
Tonkeeper, ни в любом другом TON-кошельке — восстановление по фразе перестанет
работать, а это единственный путь к средствам, если инструмент потерян.

**Следствие, требующее отдельного решения на этапе TON.** Одна TON-мнемоника
даёт **одну** пару ключей, индекса деривации там нет. Несколько TON-адресов
получают через `subwallet_id` или через разные версии контракта кошелька
(v3R2/v4R2/W5), и адрес зависит от версии. То есть «аккаунт #3» в TON — это не
то же самое, что в остальных трёх чейнах, и модель придётся расширять.

**Импортированные ключи не универсальны по чейнам.** secp256k1-ключ годится для
Tron и EVM, ed25519 — для Solana и TON, и наоборот не работает. Импорт обязан
спрашивать или выводить, к какому семейству кривых относится ключ, и показывать
аккаунт только в тех чейнах, где он применим.

### 3. Спейсы — все в одном процессе

Один запуск видит все спейсы, переключение в UI, пути вида
`/api/spaces/{space}/...`. Разблокировка — на каждый спейс отдельно, паролем.

**Почему.** Переводы между спейсами — очевидный сценарий, а с одним спейсом на
процесс он превращается в два запущенных сервиса на разных портах.

**Цена.** В памяти процесса одновременно лежат ключи нескольких спейсов.
Смягчается таймаутом авто-блокировки: спейс без активности N минут сбрасывает
расшифрованное состояние и требует пароль заново.

### 4. Миграция старых данных — только подсказка

Если при старте найден каталог `./data` с `mnemonic.txt` и `wallets.json` —
написать в лог, как перенести руками. Никакой автоматики над файлами с
мнемоникой.

### 5. UI — lit-html без шага сборки

Разметка строится теговыми шаблонами lit-html; библиотека вендорится в
`ui/vendor/`, файлы UI раскладываются по ES-модулям и отдаются тем же
`//go:embed ui`, что стоит сейчас.

**Почему без сборки.** `go install` компилирует только Go — он не запускает ни
npm, ни `go generate`. Любой сборщик означал бы, что собранное лежит в
репозитории на теге, а значит появляется постоянная дисциплина «пересобрать
перед тегом» и проверка в CI на случай, если забыли.

**Почему lit-html, а не lit целиком.** LitElement приносит веб-компоненты и
shadow DOM, который изолировал бы нынешние 488 строк глобального CSS и сломал
их. Нужен только `html` и `render`.

**Почему не Preact + htm.** Рассматривался и отклонён: htm не выпускал релизов
с 2021 года и не принимал коммитов с февраля 2024. Сам по себе он крошечный и
вендорится одним файлом, но класть замороженную зависимость в основание UI на
годы вперёд не стоит. lit-html даёт ту же эргономику и активно развивается.

**Дополнительный довод.** lit-html ложится на нынешнюю архитектуру почти один в
один: в коде уже есть объект `state` и явные вызовы перерисовки —
`renderResources()`, `renderDelegationSummary()`, `updateForm()`. lit-html
работает так же, `render(шаблон, контейнер)` по команде кода. Меняется способ
построения разметки, поток управления остаётся прежним. Preact принёс бы
компоненты с локальным состоянием и хуками — больше механики, чем нужно.

**Шероховатость вендоринга.** lit разложен по модулям с bare-импортами, поэтому
в `index.html` понадобится карта импортов — браузеры понимают её нативно — либо
один предсобранный бандл, скачанный однократно.

**Режим разработки.** Флаг, подменяющий `embed.FS` на `os.DirFS`, чтобы правка
CSS не требовала пересборки бинаря.

## Допущения, принятые без обсуждения

Это обычные инженерные решения; если какое-то не устраивает — оно меняется
дёшево, пока не написан код.

- **Опрашивается только активная сеть каждого чейна.** Сейчас баланс одного
  адреса стоит два запроса, а параллелизм ограничен двумя воркерами из-за
  лимитов публичных нод (`balanceConcurrencyPublic` в `internal/tron/service.go`).
  Умножьте на аккаунты × чейны × сети — «показывать всё сразу» на публичных RPC
  не взлетит. Сеть выбирается явно, на чейн.
- **Смена сети не перестраивает список аккаунтов**, потому что внутри чейна
  адрес от сети не зависит. Меняются только балансы и ссылки на эксплорер.
- **Спейс не привязан к чейну.** Спейс — это ключи; чейны видны все.
- **Идентификатор аккаунта — не индекс деривации.** Нужен стабильный
  собственный ID: у импортированного аккаунта индекса нет, а в разных спейсах
  индексы совпадают. Индекс остаётся полем выведенного аккаунта, но перестаёт
  быть ключом.
- **`main` остаётся в `cmd/walletspace`.** Значит команда установки —
  `go install github.com/sxwebdev/walletspace/cmd/walletspace@latest`. Если
  хочется короткой формы без `/cmd/...`, `main` надо перенести в корень модуля,
  и лучше до первого тега.

## Что ломается в нынешнем коде

| Файл                             | Что не переживёт переход                                                                                                                                          |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `internal/wallet/store.go`       | инвариант «ключи не на диске»; `Wallet{Index, Address}` как модель; `Get(index)`/`PrivateKey(index)`; fingerprint по адресу нулевого индекса — он Tron-специфичен |
| `internal/config/config.go`      | плоский конфиг; скаляр `NETWORK`; `defaultsByNetwork`; `USDT_CONTRACT`, `FEE_LIMIT_TRX`, `TRON_PRO_API_KEY` — всё это Tron-специфично и уезжает в секцию чейна    |
| `internal/tron/service.go`       | остаётся почти как есть, но становится одним адаптером из четырёх; кэши и лимиты параллелизма переезжают на уровень выше                                          |
| `internal/httpapi/*.go`          | маршруты `/api/wallets/{index}/...`; `resolveWallet` через `parseIndex`                                                                                           |
| `cmd/walletspace/main.go`        | старт: `ResolveMnemonic` → `wallet.New` → `tron.New` линеен и знает только про Tron                                                                               |
| `internal/httpapi/ui/index.html` | 2372 строки одним файлом (488 CSS, 284 разметки, 1600 JS в 73 функциях); со спейсами, чейнами и сетями это станет неподдерживаемым — см. решение 5                |

Стейкинг, делегация и деплой контрактов Tron не трогаются: они уезжают в
«операции чейна» как есть.

## Раскладка на диске

```
~/.walletspace/
  config.yaml              общие настройки: адрес, браузер, таймаут блокировки
  chains.yaml              чейны, сети, эндпоинты, ключи API
  spaces/
    default/
      keystore.json        зашифровано: BIP39-фраза, TON-фраза, импортированные ключи
      accounts.json        открыто: id, тип, индекс, метка, адреса по чейнам
    work/
      ...
```

Каталог переопределяется через `WALLETSPACE_HOME`.

Сознательное отступление от XDG: всё в одном каталоге, а не врозь по
`~/.config` и `~/.local/share`. Причина — бэкап. Инструмент держит секреты, и
пользователь должен иметь возможность скопировать один путь и получить всё.

Открыто (`accounts.json`) хранится только то, что не является секретом: адреса
публичны, метки и индексы деривации сами по себе средств не открывают.

## Модель данных

```go
type Account struct {
    ID        string            // стабильный, не индекс деривации
    Kind      Kind              // Derived | Imported
    Index     *uint32           // только для Derived
    Curve     Curve             // Secp256k1 | Ed25519 — для Imported определяет, где аккаунт виден
    Label     string
    Addresses map[ChainID]string
    CreatedAt time.Time
}
```

Ключи в keystore адресуются по `Account.ID`. `accounts.json` без keystore
бесполезен, но и не опасен.

## Интерфейс чейна

Адаптер чейна реализует общий минимум; всё сверх него объявляется как «операции
чейна» и рисуется в UI по описанию, а не фиксированными кнопками.

Общий минимум: вывести адрес из ключа, прочитать балансы (нативный + токены),
оценить стоимость перевода, построить и подписать перевод, отдать ссылку на
эксплорер.

Специфика, которая не обобщается:

| Чейн   | Что своё                                                                           |
| ------ | ---------------------------------------------------------------------------------- |
| Tron   | energy и bandwidth, стейкинг, делегация ресурсов, деплой контракта                 |
| EVM    | gas и EIP-1559, nonce, `approve` для ERC20, десятки сетей из конфига               |
| Solana | rent, ATA (счёт под каждый токен создаётся отдельно), priority fee                 |
| TON    | jetton-кошельки, версии контракта кошелька, деплой кошелька перед первым переводом |

## API

```
GET    /api/spaces                                    список, с признаком «разблокирован»
POST   /api/spaces                                    создать спейс с новой мнемоникой
POST   /api/spaces/{space}/unlock                     пароль → расшифровка в память
POST   /api/spaces/{space}/lock

GET    /api/spaces/{space}/accounts
POST   /api/spaces/{space}/accounts                   вывести следующий индекс
POST   /api/spaces/{space}/accounts/import            импорт приватного ключа
PATCH  /api/spaces/{space}/accounts/{id}              метка

GET    /api/chains                                    чейны, сети, активная сеть
PUT    /api/chains/{chain}/network                    переключить активную сеть

GET    /api/spaces/{space}/accounts/{id}/balances?chain=
POST   /api/spaces/{space}/accounts/{id}/estimate
POST   /api/spaces/{space}/accounts/{id}/transfer

POST   /api/spaces/{space}/accounts/{id}/chains/tron/stake      операции чейна
POST   /api/spaces/{space}/accounts/{id}/chains/tron/delegate
...
```

Защита от запросов через браузер пользователя (`Sec-Fetch-Site`, `Origin`,
обязательный `Content-Type: application/json`) остаётся как есть — она не
зависит от модели данных.

## Этапы

Порядок выбран так, чтобы самый рискованный шаг — хранилище — прошёл, пока
чейн остаётся один и его поведение известно.

### Э1. Хранилище, спейсы, домашний каталог

Tron остаётся единственным чейном. Меняются: keystore, модель аккаунта,
раскладка в `~/.walletspace`, маршруты со спейсами, UI-переключатель спейсов,
импорт приватников, авто-блокировка.

Готово, когда: несколько спейсов создаются и разблокируются независимо;
импортированный ключ подписывает перевод наравне с выведенным; старый `./data`
даёт подсказку в логе; все нынешние тесты переписаны под новую модель.

### Э2. Абстракция чейна и конфиг сетей

Интерфейс чейна, Tron за ним, `chains.yaml` с сетями и эндпоинтами, выбор
активной сети, кэши и лимиты параллелизма на уровне реестра чейнов.

Готово, когда: Tron работает через общий интерфейс, ничего Tron-специфичного не
осталось выше адаптера, переключение mainnet/nile идёт из UI без перезапуска.

### Э3. EVM

Ближайший к Tron по модели: та же кривая, тот же принцип токенов. Сеть — это
chain id и RPC, так что их сразу много: mainnet, sepolia, base, arbitrum.

Готово, когда: балансы и переводы ETH и ERC20 в двух сетях, оценка комиссии по
EIP-1559, `approve` как операция чейна.

### Э4. Solana

Первый ed25519-чейн, проверяет решения Э1 на прочность: другая деривация, другой
формат импортируемого ключа, ATA и rent в оценке комиссии.

### Э5. TON

Вторая мнемоника в спейсе, версии контракта кошелька, jetton-кошельки, деплой
кошелька перед первым переводом. Модель аккаунта расширяется.

### Э6. Дистрибуция

`go install`, brew tap, кросс-сборка и релизы. Не зависит от остальных этапов и
может идти параллельно с любого момента — разумно поднять сразу после Э1, чтобы
дальше проверять на реально установленном бинаре.

Для сборки и публикации логично взять собственный `gcx`; если формулы brew он не
умеет, формулу придётся генерировать отдельно.

## Открытые вопросы

**Формат импортируемого ключа.** У secp256k1 это 32 байта hex, у Solana обычно
64 байта base58 или JSON-массив из 64 чисел. Нужен разбор с однозначным
сообщением об ошибке — «неверный ключ» без подробностей здесь неприемлемо.

**Единый список аккаунтов между чейнами.** Если импортированный secp256k1-ключ
виден в Tron и EVM, но не в Solana, список аккаунтов становится разным в разных
чейнах. Надо решить, показывать ли неприменимые аккаунты серыми или прятать.

**Авто-блокировка.** Значение таймаута по умолчанию и что делать с
незавершённой операцией в момент блокировки.
